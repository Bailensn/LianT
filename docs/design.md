# 设计宗旨

LianT 是一款**自托管的跨平台聊天软件**：聊天是主体，机器人管理、回复规则和审计都只是围绕聊天的辅助能力。
目标是让使用者掌握部署权、数据控制权和技术选择权——平台只是接入点，不是宿主。
下面每一条都对应到具体实现约束，而不是口号。

## 1. 服务自主权

- 自行部署、自行决定运行环境、数据保留策略和服务边界。
- 不依赖中心化平台提供全部基础设施；平台只是接入点，不是宿主。
- 数据默认归使用者：存储路径、加密密钥、日志轮转都由部署者控制。

## 2. 隐私优先与最小化留存

- 聊天记录写入每个 Bot 自己的 SQLite（`bots/<id>.db` 的 `messages` 表），默认**不设条数上限**；
  撤回只清正文与媒体引用，保留发送者/时间的墓碑。
- 会话按「群 / 论坛话题 / 私聊 / 频道」拆分（`conversations` 表 + `messages.conv_key`）：
  同一个群里不同话题、私聊与群聊各有独立上下文，不混在一起。
- 媒体字节不落盘：库里只存取回所需的平台引用（Telegram `file_id` / QQ 签名直链）与展示元数据，
  实际下载由管理端按需代理。
- 明文凭据不写日志；token 走 AES-256-GCM 加密（`internal/secret`）。
- 能临时使用的数据不长期保存；能避免落盘的秘密不持久化。
- 安全不依赖使用者自觉，而是由存储策略和架构约束兜底（密钥 0600、数据库 0600、管理端默认只绑回环）。

## 3. 职责分离

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| Service（任务进程） | 平台连接、消息收发、业务数据、临时缓存 | 客户端界面 |
| Manager（管理端/CLI） | 配置、启停、审计查看、页面 | 直接持有平台连接 |

平台实现细节收在 `internal/platform/` 与各 runtime（`internal/bot`、`internal/qqbot`），
管理端只通过 HTTP API 和中性字段（`chat_id` / `user_id` / `message_id`）交互。

## 4. 平台适配，而不是平台绑定

- 新平台实现 `platform.Adapter` + 一个 runtime，注册即可，不改管理端契约。
- 能力差异用 `Capabilities` 显式声明（`topics` / `inline` / `webhook` / `payments` …），UI 按声明显示，不按平台名写死。
- 不强行抹平差异：QQ 的 Markdown 卡片、Telegram 的 HTML 富文本各按原生语义呈现。

## 5. 消息语义与状态准确性

消息有明确的生命周期，界面只展示能确认的部分：

| 状态 | 含义 |
| --- | --- |
| `received` | 群内收到该消息（本地观测到） |
| `sent` | 平台已受理这条发送请求（**不等于**送达或已读） |
| `recalled` | 已在平台侧撤回；正文清除，仅保留墓碑 |
| 其他 | 原样展示，不猜测、不伪造一致性 |

- 撤回是状态，不是「消息从未存在」：条目保留时间与发送者，正文置空。
- 「已发送」的 tooltip 明确写出平台不提供送达回执。
- 未知/过期/不可寻址的状态原样显示，而不是映射成「成功」。

## 6. 模块化与可演进

协议（`internal/ipc`）、服务端 runtime、管理端（`internal/admin`）、平台适配层各自独立演进；
兼容性通过明确的边界（HTTP 契约、`Capabilities`、数据库 schema 版本）保证。

## 7. 原生体验与实现独立

- 不要求所有客户端共享同一套视觉实现；当前管理端是 HTML，未来可以有原生客户端。
- 协议与业务语义保持一致，界面可充分利用各平台能力。

## 8. 取舍

宁可显示「状态未知」，也不伪造一致；宁可少存一条消息，也不默认长期留存；
宁可多一个 adapter，也不把平台差异塞进业务分支。
